1 System Overview

The Bodaboda Management System (BMS) is a web platform commissioned by a Kenyan county authority to register, verify, and manage motorcycle taxis (bodabodas). It provides end-to-end workflows for motorcycle owner registration, rider onboarding, annual fee collection, public verification, incident reporting, and administrative oversight — all backed by a Supabase PostgreSQL database with Row Level Security.

Core Purpose Replace paper-based bodaboda registration with a digitised, searchable, QR-verified system. Every registered motorcycle is assigned a QR code and every rider receives a printable BMS ID card.

High-Level Architecture

Single-page React app (Vite)
Supabase backend (DB + Storage)
Row Level Security on all tables
OTP phone verification at registration
QR code verification (public, no login)
Printable digital ID card (PDF)
Three payment gateways
Role-based admin access control
Full audit trail for all admin actions
OCR auto-fill from ID document photos
GPS tracking integration (separate service)
Incident reporting and appeals

5 Authentication

Owners & Riders — OTP Phone Verification

There is no Supabase Auth for public users. Instead:

  1. 1User submits phone number during registration
  2. 2A 6-digit OTP is generated, stored in the otp_codes table, and sent via SMS
  3. 3User enters OTP to verify. On success, owners.otp_verified = true
  4. 4Owner/rider ID is persisted in localStorage to maintain session across page refreshes
  5. 5No JWT or token is used — session is purely the UUID stored client-side
Security Note This is a lightweight session model appropriate for a registry system. If stronger authentication is required, integrate Supabase Auth and link auth.uid() to owner/rider records.

Admins — Username + bcrypt

  1. 1Admin enters username + password on the admin login screen
  2. 2Server-side: fetch system_users row, compare with bcrypt.compare()
  3. 3On success: load role + permissions, write login event to user_activity_logs
  4. 4Increment failed_login_attempts on failure; set locked_until after threshold
  5. 5Admin session held in React state; refreshing the page requires re-login

6 Owner Registration Flow

A multi-step form that creates one owners row, one motorcycles row, and one verifications row.

  1. 1Personal details: full name, phone number, national ID, next of kin name and phone
  2. 2OTP verification: SMS OTP sent to phone. Must verify before proceeding
  3. 3OCR (optional): User can upload a photo of their national ID; Tesseract.js extracts name and ID number to auto-fill fields
  4. 4Motorcycle details: registration plate, make, model, tracking device ID (optional), insurance policy number
  5. 5Document upload: bike photo, logbook, KRA PIN certificate, insurance cover. All uploaded to Supabase Storage. Public access enabled for viewing; URLs stored in motorcycles table
  6. 6Payment: KES 350 via M-Pesa, SalamaPay, or eCitizen. See Section 8
  7. 7Completion: Insert owner + motorcycle + verification records. Generate QR code pointing to /verify/{qr_code_data}. Show success screen with QR download
QR Code Token qr_code_data is a UUID stored in verifications. The public verification URL is {origin}/verify/{token}. This token is stable and does not encode sensitive data.

7 Rider Registration Flow

  1. 1Personal details: name, national ID number, phone, next of kin
  2. 2Professional details: county registration number, SACCO ID, stage name
  3. 3OCR (optional): ID photo upload for auto-fill via Tesseract.js
  4. 4Document upload: passport photo, driving license, good conduct certificate, ID copy — all to Supabase Storage
  5. 5Payment: KES 100 via M-Pesa, SalamaPay, or eCitizen
  6. 6Completion: Insert rider record with assignment_status = 'Unassigned'. Generate BMS ID

BMS ID Generation

The BMS ID is a unique alphanumeric identifier for the rider (e.g. BMS-2026-00342). It is generated client-side using a counter + year prefix and stored in riders.bms_id. See Section 14 for the ID card format.

8 Payment System

Motorcycle Owner Annual Fee
Covers January – December of the payment year
KES 350
Rider Annual Fee
Covers January – December of the payment year
KES 100
Critical: Year-Based, Not Rolling Fees cover a fixed calendar year (Jan 1 – Dec 31). A fee paid in November 2025 covers only 2025 and expires on January 1, 2026. There is no proration. Payment due logic: MAX(payment_year WHERE status='completed') < currentYear.

Payment Due Detection

On dashboard load, query the latest completed payment for the user:

SELECT payment_year FROM payments WHERE user_id = $1 AND user_type = $2 AND payment_status = 'completed' ORDER BY payment_year DESC LIMIT 1; -- If result.payment_year < new Date().getFullYear(), payment is due. -- If no rows returned, payment is due.

Payment Methods

MethodFlowTransaction Reference Format
M-Pesa User enters Kenyan phone number. Receives simulated STK push. Enters M-Pesa PIN to confirm. QRS{8-digit timestamp}{4-char random}
SalamaPay Same phone-number flow. Connects to SalamaPay wallet. SAL-TXN-{8-digit timestamp}{4-char random}
eCitizen User visits ecitizen.go.ke, pays under Transport & Licensing → Bodaboda Annual Fee, then enters the reference number from eCitizen to confirm. Reference entered by user (validated: 6–20 alphanumeric characters)

Payment Modal States

The PaymentModal component has 5 steps: select (choose method) → details (enter phone/reference) → processing (2.5s simulation) → success or failed.

On success: update payments.payment_status = 'completed', update owners.payment_status (or riders), set payment_id to the payment UUID.

UI Behaviour When Payment Is Due

The payment card on both Owner and Rider dashboards switches from emerald green to red, shows an alert triangle with the due year, and displays a "Pay Now — KES {amount}" button that opens the PaymentModal directly.

13 Incident Management

Incident Lifecycle

  1. 1Reporter submits incident via public verification page (or admin creates one)
  2. 2Incident created with status = 'open'. Notifications sent to affected owner and rider.
  3. 3Admin reviews — can add notes, change status to under_review. Can upload evidence.
  4. 4Rider can file an appeal: text + evidence files. Appeal status: pending → approved / rejected.
  5. 5Admin writes response, marks response_type (email/sms/phone), sets response_sent_at.
  6. 6Final status: resolved or dismissed.

Notification System

Two tables handle notifications: incident_notifications (linked to a specific incident, for both owners and riders) and rider_notifications (general purpose inbox for riders with title/message/read flag). Unread count shown in the rider dashboard bell icon.

15 GPS Tracking — Raidar Integration

Separate Service GPS tracking is handled by a standalone project called Raidar. It has its own Supabase instance and Node.js backend. The BMS frontend embeds a read-only tracking modal that connects to the Raidar API.

Raidar Features

Real-time GPS position on Leaflet map
Historical route playback
Geofence creation and entry/exit detection
JT/T 808-2019 GPRS protocol over TCP
Device alarm management
REST API with API key authentication
Webhook support for events
Rate limiting and usage analytics

Raidar Database Tables (separate instance)

tracking_devices, device_locations (partitioned by time), device_alarms, geofences, device_commands, api_clients, api_usage_logs, device_connections, vehicles. PostGIS extension enabled for spatial queries.

Integration in BMS

The TrackingModal component in the admin/owner dashboard fetches live position from the Raidar REST API at http://localhost:3000/api (configurable). The motorcycle's tracking_device_id is the link key between the two systems.

17 Row Level Security

Every table has ALTER TABLE ... ENABLE ROW LEVEL SECURITY. Policies are written per-operation (SELECT / INSERT / UPDATE / DELETE).

Important Pattern Because owners and riders authenticate via OTP (not Supabase Auth), RLS policies for their tables use TO anon with permissive rules rather than auth.uid(). Sensitive filtering is done in application code. For production hardening, link owners/riders to Supabase Auth UIDs.

Admin Table Policies

Admin tables (system_users, user_roles, user_activity_logs) are restricted to authenticated role or service role key only. Never expose these via the anon key.

Public Read Tables

verifications, motorcycles (registration/status fields only), riders (non-sensitive fields), rider_history — these support FOR SELECT TO anon USING (true) to power the public verification page.
